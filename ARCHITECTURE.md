# ARCHITECTURE

## Shape
A static web app. Phaser draws the game. Plain DOM draws menus, modals, banners, and captions on top. Game rules are pure TypeScript with no Phaser imports.

```
Browser
 ├─ Phaser scenes (draw, animate, play sound)      src/scenes/
 ├─ DOM overlays (modals, banners, captions)        src/ui/
 ├─ Pure game rules (tested)                        src/game/
 ├─ Question bank + picker (tested), topic tags     src/questions/   (multiplication: Past, division: Future)
 ├─ Sound manager (unlock on tap, mute, volume)     src/audio/
 └─ Storage wrapper (localStorage, try/catch)       src/storage/

App server (one Node process on Railway)            app-server/, voice-server/
 ├─ Static files from dist/ + security headers      app-server/static.ts, headers.ts
 └─ GET /v1/clips/:id from db/voice-*.sqlite        voice-server/clips.ts (read-only)
    (the five intro cards are static .m4a files in public/audio/voice/, not served from a database)
```

## Voice clips (content)
Spoken audio for wipeout lines is pre-made offline and stored in SQLite files under `db/` (`voice-k4.sqlite`, `voice-5-8.sqlite` and `voice-9-12.sqlite`). Question text is not spoken any more (owner decision, 2026-10-23), so the question clips in those files are unused. Each clip id is `t:` plus a 64-bit FNV-1a hash of the exact text (`src/audio/clipId.ts`), so the player can look a clip up from the text it would speak. The voice says a reworded form (`src/audio/toSpoken.ts`); captions and ids use the original text. The app server serves them (next section) and the databases are not in the web bundle. Details: `db/README.md`.

## App server and voice clips
`app-server/` is a small Node server (`node:http` only) that serves the built site and the recorded lines on one origin: `GET /v1/clips/:id`, `GET /health`, static files with cache headers, compression and Range support. The exact security headers come from `public/_headers`. The game asks for clips only in a build made with `VITE_VOICE=on` (production and e2e builds). `speak(line)` picks the line's own `audioSrc` file, then a clip (`src/audio/clipPlayer.ts`, id from `src/audio/clipId.ts`), then the browser voice. A clip that fails or takes over 1.5 s falls back at once and is not asked for again that session. The funny knock-down line is also spoken through `speak()` when clips are on. The Phase 4 relay will mount at `/ws` in the same process. Full contract, env, and Railway cutover and rollback: [docs/APP_SERVER.md](./docs/APP_SERVER.md).

## Scene flow
New family: TapToStart → Intro → Loading → Setup → Camp → Battle Plan → Battle → Victory → Rematch or Camp. The Battle Plan is a DOM screen run by the Camp step (`showPlan`, `src/ui/planScreen.ts`). Back returns to the Camp. Lock it in! saves the plan and starts the match.
Returning family (intro seen and players saved): Loading → Camp → Battle → Victory → Rematch or Camp. There is no Tap to Play screen for them. The first tap or key press anywhere unlocks sound (`boot.ts`), so nothing plays before a tap.

Match length: Setup has a Match length choice (Short, Normal, Long) on the button row. Normal is the default and is exactly the base balance (400 base health, see docs/GAME_SPEC.md "Pace"). `MATCH_LENGTH.healthScale` in `src/game/config.ts` (0.5, 1, 1.5) scales full base health (and full fighter health when `CHARACTER_HEALTH` is on) in `createMatch` through `scaleHealth` in `src/game/matchLength.ts`. It never changes shots per turn, questions, reload timing or scoring. `buildBattleData` reads the saved length into `MatchOptions.matchLength`; an unknown value is Normal.

Back and exit: Setup has Back (to the Camp, saves nothing) once players are saved. The Forge has Back. In a battle, Pause offers Keep playing and Leave game, which asks "Leave this game?" first (Stay is focused) and then returns to the Camp.

The Camp is home. A returning family (players saved) goes Loading → Camp. A new family goes through Setup first. "Change players" on the Camp opens Setup again. The Camp reads the players Setup saved, so no data passes between the two. "Time to Clash!" starts a fresh seeded match. A Camp with no saved players goes back to Setup.

The Camp hawk is a small 3D solid (`src/ui/hawkModel.ts`: body, head, beak, eyes, two thick wings, tail). Each frame it is turned about its upright axis, painted back to front in flat colors with an outline, so it keeps its volume at every angle. `hawkPose` in `src/ui/flightPhysics.ts` is the pure pose math (position, size, depth, over/behind flag, yaw, wing lift, dim, shadow; tunables in `HAWK_3D` and `HAWK_ORBIT`). The hawk circles in 3D around the title: on the near half it is painted in a second SVG layer placed over the title (`hawkFrontLayer`, larger, with a soft shadow), on the far half in the scene layer under it (smaller, dimmed). It switches layers exactly at the two turns. With reduced motion the scene draws a still three-quarter pose.

## Turn your iPad (landscape only on tablets)
`src/ui/turnScreen.ts` mounts one full-screen dialog (`data-testid="turn-screen"`, z-index 200, above the covers). It shows when the window is taller than wide, the short side is 600px or more, and the main pointer is coarse (a finger). That keeps laptops and tall mouse windows out and leaves phones alone. It listens to `resize` and `orientationchange` only, no timers. While it is up, the rest of the page is `inert`, focus moves to it, and a running battle is paused through the normal Pause button (nothing is lost). Time spent there is added to `awayMs()`, which the default overlay clock subtracts, so a reload question is not timed while the iPad is upright. Booted from `bootApp`. Tests: `tests/ui/turnScreen.test.ts`, `e2e/turn-screen.spec.ts`.

`src/scenes/battle/aimArt.ts` draws one small angle guide (a short arc, a ~108px line, a tiny handle with a 48px invisible grab circle, and the degree number) at the muzzle of the fighter about to fire. The muzzle comes from `firingOrigin(team, unitId, layout)` in `src/game/units.ts`, the same function `match.fire()`, the bot and the dotted preview use, so the guide, the preview and the shot always start at one point. `flow.ts` sends it to the view as `ViewStatus.firingOrigin`, and picking another fighter moves the guide. Dragging the tip sets the angle only (`angleFromDrag` in `geometry.ts`). The degree number goes where `angleLabelBox` in `src/scenes/battle/angleLabel.ts` (pure) puts it: just past the tip, or the nearest spot a little further out or a little turned that covers no fighter (body, letter tag or the picked arrow, from `fighterKeepOut`) and not the guide itself. It stays inside the world and above the ground line, and it prefers a spot off the solid shapes when one is close by. `tests/scenes/battle/angleLabel.test.ts` sweeps every fighter, castle place, base spot, biome and angle at the largest label size (`ANGLE_LABEL_MAX`), and `e2e/phase2.spec.ts` checks the real label fits that size. Power is shown and set only by the bottom-bar slider; there is no power meter on the board. The e2e hook reads the guide through `window.__timeclash.aim()`. The dotted preview comes from `match.previewShot()`, which flies the same shot as `fire()` (fighter range, ammo, walls) and changes nothing. After a shot, `showTrace` leaves the full arc up as faint dots (`traceDots` in `trajectory.ts`). The flow clears it before the pass screen and before the reload question, so no cover ever has it behind it. Wind already shows once in the HUD with arrows and a number, so the arc adds none. Tests: `tests/game/units.test.ts`, `tests/game/previewShot.test.ts`, `tests/scenes/battle/geometry.test.ts`, `tests/scenes/battle/angleLabel.test.ts`, `tests/scenes/battle/trajectory.test.ts`, `e2e/aim.spec.ts`.

## Base deployment spots (Phase 2)
`src/game/spots.ts` turns a spot id (`skyscraper`, `bridge`, `foodTruck`, or `null`) into a `BattleLayout`. Only Team Future's base, launch origin, and cover move. `null` and unknown ids give the Phase 1 layout. The numbers live in `SPOTS` in `src/game/config.ts`. The Battle Plan picks one (see below).

`src/game/forts.ts` is the mirror for Team Past: a castle place id (`hillFort`, `villageWall`, `drawbridge`, or `null`) moves only the Past castle, its launch origin and its cover (`FORTS` in config, same shape as `SPOTS`). `null` and unknown ids give the Phase 1 castle in the rules code. The live game always passes one: Village Wall is the default (`DEFAULT_PLAN.fort`).

## Battle Plan, biomes, ammo and evasion (Phase 2, wired in)
- **Battlefield.** `src/game/battlefield.ts` `buildLayout({ biome, spot, fort })` builds the `BattleLayout`: obstacle 0 is the biome's middle shape (`BIOMES` in config; aspen is the Phase 1 hill), then the spot's shapes, then the castle place's shapes. The layout carries `biome`, `spot`, `fort` and `baseShift` (both teams). A `BattlePlan` always has a `fort`: `normalizePlan` gives a plan saved before it existed Village Wall. `buildLayout` still accepts a missing or null `fort` (the Phase 1 castle) for tests and old callers.
- **Obstacle art.** `src/scenes/battle/obstacleArt.ts` (pure) names each obstacle's look from the layout (`obstacleKinds`) and returns its shapes (`obstacleArt`): the exact collision polygon, details kept strictly inside it, then its outline. One documented exception to "the picture equals the solid shape" (Andy approved it on 2026-10-24): the supports that hold up a floating shape (`obstacleDecor`: the Drawbridge's gate post, two chains and a leg; the Future bridge's two pylons and its cables) are decoration, marked `solid: false`. They never change a collision polygon, shells fly through them, they stay inside the world and never go below the ground line, and `layoutPaint` paints them before every solid shape, so each outline stays on top. `backdrop.ts` paints `layoutPaint` with `paintArt`; `BattleScene.setWalls` paints the Stone Wall ability with the same recipe. A fighter standing on its base (`ridesBase` in `units.ts`) moves with it, and `firingOrigin` applies the shift, so the shot, the bot and the guide agree. The scene draws the biome backdrop (`src/scenes/battle/biomeArt.ts`) and shifts those fighters.
- **Ammo.** Special kinds are unlocked per player and side on the Battle Plan (`unlockAmmo`, saved as `loadout[team].ammo`). `MatchOptions.ammo` lists the kinds each side owns. The match keeps the loaded kind and the shots left (`selectAmmo`, snapshot `ammo` and `ammoLeft`). Firing a special kind uses one. At 0 it goes back to Standard. Standard changes nothing.
- **Evasion.** `src/game/evasion.ts` is a small cycle per team: ready → armed (this turn) → active (the other team's next turn) → recharging or used. `armEvasion` and `disarmEvasion` work only while aiming and are free. Team Past's Stone Wall adds a wall obstacle (`EVASION.barricade.wall`) for the whole enemy turn, once per match (`currentLayout()`). Team Future's Hoverboard Dodge makes the first damaging hit of the enemy turn miss (`dodged: true`), before the force field, and is ready again 2 own turns after it was armed. Misuse throws (`IllegalTransitionError` out of phase, `EvasionError` when not ready).
- **Screens.** The HUD gear (`src/ui/hudGear.ts`) floats by Fire: an Ammo button (hidden until a kind is owned) and the ability button (`aria-pressed` when armed). With no room it shows icons only. Chrono says a line with a caption when an ability is armed.

## Base builder (Phase 2, behind a switch)
Before a battle a player builds a castle (Team Past) or a base (Team Future) from bricks. It is the only Build Base screen: the old Scrap shop for upgrades and the `?builder=0` switch were removed on 2026-10-25, so upgrades cannot be bought. A level saved on a device still loads (`src/storage/storage.ts`) and applies in battle (`matchEffectsFor` in `src/game/loadout.ts`). The Camp has one Build Base button. The builder has a Past and Future picker like the Forge: `showBaseBuilder` resolves with the other team when it is tapped, and `runCampStep` opens it again for that side. Built bases are used in battle (`BASE_IN_BATTLE` is on): `runCampStep` passes `battleBasesFor(bases, names)` into the match.
- **Rules, no Phaser or DOM:** `src/game/baseBuilder.ts`. A catalog of pieces per team (id, size in cells, hit points, free or locked), a plot of 24 by 12 cells (the bottom row is the foundation), and pure operations that return a new `BuildState`: `placePiece`, `movePiece` (optionally with a new turn), `turnPiece`, `removePiece`, `clearBuild`, `undoBuild`. The rules: inside the plot, no two bricks share area, and every brick is held up all the way down to the ground (owner, 2026-10-24). A brick is held up when its bottom edge sits exactly on the foundation, or on top of a held-up brick with at least half a cell of overlap sideways (`BASE_BUILDER.minSupportSteps`, 4 steps). A corner touch, a gap, or a brick stuck to the side of a wall does not count. Shapes of your own rest by their filled squares (`restOverlap`, `heldUp`). A brick in mid-air is refused with `floating`. Removing, moving or turning a brick that another brick rests on is refused with `holding` (take the top off first); a short slide that still holds the top brick is fine. Clear and Undo always work, and every Undo step is legal because only legal edits are kept. `placeProblem(pieces, cand, skip)` gives the reason. With Snap off a brick sits on a finer grid (`ox`, `oy` in eighths of a cell). A brick let go less than one cell above something drops onto it (`dropOnto`, at most `dropSnapSteps`). Turn is a quarter turn about the middle and slides to the nearest legal spot. A drop onto another brick lands on the nearest legal spot (`landingFor`, `findSpot`), never in mid-air.
- **Saving:** three slots per player name and side in `timeclash.bases`, keyed like the wallets (`walletKey`). A base is stored as small tuples `[piece, x, y, ox, oy, rot, hp]`. `repairBase` cleans everything read from storage (a bad brick is dropped, the rest stay) and then settles it (`settleBase`): a brick saved floating before the support rule drops straight down, lowest first, then leftmost, until it lands on the foundation or a held-up brick. A brick that cannot land (it would rest on a corner only) is taken off as a last resort. A pinned weapon pad rides down with its brick (`repairSpots`). `parseBases` cleans storage without settling, so the builder can tell (`baseWasSettled`) that an old base was set down: it saves the settled base and says so once in the status line. The battle reads the settled base through `chosenBase`.
- **Scrap:** a locked piece is unlocked with `unlockPiece` in `src/game/economy.ts` (same rules as the Forge: no negative Scrap, one purchase per piece). Unlocked ids are kept in the wallet at `loadout[team].pieces`. All numbers live in `BASE_BUILDER`.
- **Weapon spots:** a base has four pads (`B.spots.count`). `BuildState.spots` holds `{ weapon?, mine?, x?, y? }` per pad (`mine` is the pad's copy of a weapon of your own), and `assignWeapon`, `clearSpot` and `moveSpot` return a new state like the brick operations, so Undo covers bricks and weapons together. `resolveSpots(pieces, spots)` works out each pad's place: spread across the built base and resting on the highest brick under it, or a row on the foundation when there are no bricks. The weapon catalog (`SPOT_WEAPONS`, built from `BASE_BUILDER.spotWeapons`) carries a role, damage and hp for the later battle task. A locked weapon is unlocked with `unlockSpotWeapon` (wallet field `mounts`). Saves add an optional `s` array to each slot, so old saves load unchanged.
- **Your own shapes:** `src/game/customShapes.ts` holds the pure shape rules: a 6 by 6 pad, squares that touch side to side, at most 12, trimmed, each square with a material (`Cell = [col, row, material?]`, no material is the side default), the canonical key (one letter a square: `0` empty, `1` default, `w` `m` `g` `j` for wood, metal, glass, jelly, as in `w0/10/1g`), quarter turns that keep materials, the side's materials (`materialsOf`, from `BASE_BUILDER.teamMaterials`), hit points from materials (`shapeHp`, `BASE_BUILDER.materialHp`) and the shape name rules (`shapeNameProblem`, the Workshop's `nameProblem` at 14 letters). A shape is a piece whose id is `own:P:<key>` or `own:F:<key>`, so a saved base carries the whole shape with its materials, and a deleted shape stays in every base that uses it. `parseCustomId` refuses a material the side does not have and a default written by its letter, so each shape has one id. `pieceById` reads these ids, `occupiedRects` gives one box per filled square for collision and support, and the saved list per player and side is `shapes` (keys) plus `shapeNames` (name by key, optional, so an old save loads with "Shape N") inside `timeclash.bases`, managed by `saveShape` (with a name), `deleteShape`, `shapesOf` and `savedShapes`. The screen draws each material with its own pattern (`materialSquare` in `baseBuilderArt.ts`). Pad words are in `src/data/shapeCopy.ts`.
- **Screen:** `src/ui/baseBuilderScreen.ts` (plain DOM, pointer events, keyboard), pictures (bricks, pads and weapon icons) in `src/ui/baseBuilderArt.ts`, styles in `src/styles/baseBuilder.css`. Layout: the top bar holds Back, the three saved bases and Scrap. A left rail holds Team (Team Past, Team Future), then Mode (Build, Weapons) and the spots count. The right rail holds Turn, Undo, Clear, Snap and Done. Nothing sits on the plot, and the plot picture fills its frame exactly (`innerBox`), so every pixel of it is a place to build. A brick let go just past the plot edge (`EDGE_GRACE_PX`) is pushed back inside. A brick is placed by a drag from the tray, or by a tap on a tray brick and then a tap (or a slide) on the plot; with a mouse the picked brick shows where it would go. A placed brick is moved by a drag and chosen by a tap. A refused drop shows a pink dashed outline and the reason in the status line. The Camp shows a Build button and a small picture of the chosen base per side (`campScreen.ts`), and `runCampStep` in `src/scenes/steps.ts` opens the builder and returns to the Camp on Done.
- **Not built yet:** the battle scene does not read the base. See `docs/BUILD.md` for how it will.

## Weapon Workshop (Forge, make your own weapon)
"Make my own weapon" in the Forge opens the Workshop (`src/ui/workshopScreen.ts`). Rules are pure in `src/game/customWeapons.ts`, numbers in `WORKSHOP` (config).
- **Design.** A style is one of the side's three catalog weapons (`base`: short, long or heavy). The player spends up to `WORKSHOP.budget` points (10) on `power`, `reach` and `splash`, each 1 to 5. `customStats` turns points into `direct` (19 to 31), `near` (6 to 14) and `speedScale` (1.0 to 1.2). `powerScore = direct + near + 20 x (speedScale - 1)`; the best custom score is 43 and the best catalog score (Iron Cannon, Rail Cannon) is 48, pinned by a sweep of every legal design at every level.
- **Saved shape.** An optional `custom` list on `TeamLoadout`: `{ id, base, name, power, reach, splash }[]`, at most 6 per player and side. The id is `custom:P:<n>` or `custom:F:<n>` (`parseCustomWeaponId` accepts nothing else, so a bad id never reads as a catalog weapon). A custom weapon is owned through the same `owned` map (level 1 to 3) and can be the `weapon` in use. `cleanCustomList` checks the list on every read: a bad entry is dropped, the rest stay. Old saves have no `custom` field and load unchanged.
- **Use.** `weaponFor(team, loadout, id)` finds a catalog or custom weapon, so `effectsFor` and `matchEffectsFor` read a custom weapon exactly like a catalog one, Forge levels included. `forgeCustomWeapon` (economy) pays the Scrap from the `WORKSHOP.cost` table (6 to 24, by score), adds it, owns it and equips it. `equipWeapon` takes custom ids.
- **In Build Base.** `customMountWeapons(camp, name, team)` in `src/game/customMounts.ts` returns the side's custom weapons as `SpotWeaponDef`s (role from style: direct, volley, lob; damage and hp from the points and `WORKSHOP.mount`; `art`, the catalog picture of its style; `mine: true`; no Scrap). The builder lists them as "My weapons" at the top of the Weapons-mode list. A mounted one is stored on the pad as a copy (`Spot.mine`, saved as `m: { b, n, p, r, s }`), checked with `cleanCustomList` on every read, so a renamed or lost Forge weapon never breaks a base and old saves load unchanged. `spotDef(spot)` and `ResolvedSpot.custom` give its spot weapon.

## Turn state machine
`PASS_SCREEN → AIMING → SHOT_1 → AIMING → SHOT_2 → RELOAD → NEXT_PLAYER`. A turn has exactly two goes. A go is one helper's command: a launcher shot, or a dasher's Walk out or Come back. Illegal moves throw. Tests pin every legal and illegal transition.

## Fighters
Each team has five fighters in `src/game/units.ts` (`UNITS`, `unitsOf`, `unitById`, `DEFAULT_UNIT`). Past: A Hot Air Balloon, B Archer, C Cannon Knight, D Catapult, E Spearman. Future: 1 Tank, 2 Helicopter, 3 Missile Bunkers, 4 Saber Robot, 5 Laser Gun Robot. Only one acts at a time. In AIMING the player calls `selectUnit(id)` (free, not a shot). The Match snapshot has `selected` per team, remembered between turns, and each `lastShot` records its `unit`. A fighter sets where the shot starts (`origin`), its range (`speedScale`, times the weapon's) and its damage (`damageScale`, times the weapon's, rounded, never below 1). Mirror pairs (A~2, B~5, C~1, D~3, E~4) share both scales. No fighter's `damageScale` is above 1, so a perfect turn never beats 88 (docs/GAME_SPEC.md "Pace"). The defaults C and 1 are the old launchers, so a fresh game plays exactly as before (`tests/game/squadGolden.test.ts`).

Character health (flag `CHARACTER_HEALTH.enabled`, off): every fighter has 4 health in `Match.unitHp`, a team loses when all its fighters are knocked out, and base health is unused for the win. See `docs/GAME_SPEC.md` "Character health".

Built bases in battle (flag `BASE_IN_BATTLE.enabled`, on since 2026-10-25): a team's built bricks take hits and fall in the match (`src/game/builtBase.ts`, `match.ts`). With character health off (the live game) the bricks are the base health: `createBuilt(bases, { layout, flatHp })` fits each base into its old footprint (`fitFrame`) and shares the starting health out (`healthPlan`), `shotLanded` scores a shell on the brick it stopped at or the closest one, and `baseHp` is `builtHealth` (0 once the foundation is gone). The scene draws it with `src/scenes/battle/baseLayer.ts` (Phaser) and `basePlan.ts` (pure: sprites, wear, crumble); bricks are the builder's SVG pictures (`brickSvg`) turned into textures. The flow calls `view.playBricks(team, fell, bricks)` after a blast or a bonk. The weapons on the pads fire in this mode too: `createBuilt` makes a mount (`mount:0` to `mount:3`) for every filled pad (a weapon of your own from `ResolvedSpot.custom`, else the catalog), with a hit box the size of the drawn pad and `mountScale` (its damage next to a fighter's, capped at `BASE_IN_BATTLE.baseHealthMount.maxScale`). `shotLanded` scores each shell of a go on its own (`scoreShell`: a brick, the brick under a pad, or the closest brick), then the Shield generator (`guardFor`), the dodge and the force field each take a whole go, and a pick whose pad fell goes back to the fighter (`dropFallenPicks`). The HUD gets `mounts` and `selectedMount` in `HudState`, and "Pick one" shows a Base weapons token (`src/ui/hudView.ts`). The flow starts the guide, the wind-up and the shells at the pad, flies a volley's shells together, and calls `view.setSelectedMount` (a ring on the pad) and `view.flashPad` as it fires (`BaseLayer.markPad`, `BaseLayer.flashPad`; `padRing` and `padFlash` in `basePlan.ts`). With character health on, the older rules apply. See `docs/GAME_SPEC.md` "Weapons on the pads". Fighters on a built base (2026-10-25): `src/game/riders.ts` (pure) puts each fighter that rides the base (`RIDER_IDS`) on the highest standing brick under its feet (`riderDrop`, `riderOrigin`; feet from `BASE_RIDERS.foot` in config, pinned to `UNIT_BOXES`). `match.ts` (the shot and the preview), `bot.ts` (on the real field, not its flight copy) and the flow (`shooterOrigin`) all read it. After a crumble the flow compares `riderDrops` before and after (`riderFallsFor` in `src/scenes/battle/riderFalls.ts`), calls `view.playRiderFalls(team, falls)` alongside `view.playBricks`, then says a line from a seeded per-team bag (`createBaseFallLines`, salt `RNG_SALT.baseFalls`): a bubble, the caption bar, and the voice when clips are on. The scene draws the fall with `src/scenes/battle/riderArt.ts` (`RiderLayer`) from the pure frames in `riderFall.ts`, turning the fighter round its feet. `fighterKeepOut(layout, drops)` and the aim art read the current drops, and the e2e hook's `bricks()` lists each base's `riders`.

Squads S1 (flag `SQUADS.enabled`, on; `MatchOptions.squads` overrides it; ignored with character health or built bases): each side also has a launcher helper (today's fighter and aim, fired with `fire()`) and one walking dasher, in `src/game/crew.ts`. A `Helper` has `state` (`home`, `out`, `resting`), `spot` (`g0` to `g4` while out), `hp` and `readyAt`. In AIMING a player calls `selectHelper(id)` (free), then `fire()`, `dash(spot)` (the one stop `helperTargets()` lists) or `recall()`. A dash or a recall is one whole go: each runs FIRE and SHOT_LANDED itself, so the turn machine is unchanged and the third go, a skipped reload and the Power Shot all behave as before. The Power Shot is always the launcher's. `ready()` now returns the start-of-turn bonks (`StandBonk[]`, from `planStand`): every out dasher walks on if nothing is next to him, then bonks the enemy dasher beside him or the enemy base from his attack spot (`g3` for Past, `g1` for Future). A base bonk goes through the gate cut (`nearCut`), a Hoverboard Dodge and a force field like a shot, and can end the match. `shotLanded()` adds `dasher` (a `DasherHit`) when an enemy shell lands near an out dasher (`hitDasher`, the fighter hit box `CHARACTER_HEALTH.box` at his spot). The snapshot's `squads` adds `maxHp` and `ownTurns`. With the flag off the snapshot has no `squads`, `ready()` returns `[]`, and the new calls throw `IllegalCommandError('flag_off')`. The scene draws only what the flow tells it: `syncSquads`, `walkDasher`, `playDasherBonk`, `playDasherHit` on `BattleView`. See `docs/SQUADS_PLAN.md` "S1 as built".

## Ammo (rules; wired in through the Battle Plan, see above)
`src/game/ammo.ts` holds four kinds: standard, confetti explosives, bouncy plasma spheres and heavy iron bowling balls. Standard is free, unlimited and changes nothing (`tests/game/ammo.test.ts` pins that). The other three cost Scrap to unlock (10, 14, 18) and have 3, 3 and 2 uses per match. `simulateShot({ ..., ammo })` applies speed and wind scales and the plasma bounce (once, off the ground only; the result adds `bounced`). `classifyBlast(impact, base, radiusScale)` widens the blast for confetti. `scaleDamage(base, ammo)` scales and rounds damage. An unknown id counts as standard.

## The hit moment
A hit gets a burst (`playHitBurst`: a flash, an expanding ring, 14 flying bits and a puff, fire for Team Past and cyan and white for Team Future, gone in under 0.9 s) on top of the explosion, a floating "-N" pip over the base that was hit, and a pop on that base's health number. A near miss also knocks the defender down: a hop, a spin, a bounce, then lying still with 3 circling stars until the next turn, when the fighter stands back up. The fall style (face-plant or backward flop) comes from the match seed (`fallVariantFor`). The wipeout line comes from `tumblePool(team)` in `src/data/copy.ts`: shared lines plus that team's own. All numbers are in `HIT_FX` in `src/game/config.ts`. The plans are pure and tested (`src/scenes/battle/hitFx.ts`, `tumble.ts`). One flash limiter (`flashAllowed`) keeps every screen flash under 3 a second. With reduced motion on: a short fade, the final fallen pose, the bubble and the pip, with no flying or spinning.

## Computer player (one child plays alone)
On for everyone (`PRACTICE_BOT.enabled` in `src/game/config.ts`, owner decision 2026-10-24). `?computer=0` on the address switches the choice off and `?computer=1` switches it on, whatever the flag (`practiceEnabled` in `src/game/practice.ts`, the same pattern as `baseBuilderOn`, read once in `createServices` into `AppServices.computerPlayer`). With it off, Setup, the Camp and the battle are unchanged, and a saved choice is ignored.
- **Rules (pure, `src/game/`):** `bot.ts` picks the shot and the reload answer. `practice.ts` decides who the computer is (`withComputer`, `computerTeamOf`, `practiceRun`), whose turn is the computer's (`isComputerTurn`), who sees the pass screen (`needsPassScreen`: nobody when one child plays alone) and the pacing (`aimDurationMs`, `aimSteps`, `reloadWaitMs`). Pace numbers are in `PRACTICE_BOT.pace`.
- **Walls and obstacles:** the search flies its test shots on the field it is given (so the biome's middle shape is always counted) plus the Stone Wall while `state.evasion` shows Team Past's barricade as active (`wallsInView`). Only public state is read. The aim error and wind skill still apply on top, so easy and medium miss often. `botPlay.ts` can raise the wall (`raiseWall`) and take a `layout` for the 240-match simulation in `tests/game/botWall.test.ts`.
- **Setup:** `showSetup(..., { computer: true })` adds the Play with row and the Computer player card (`src/ui/computerPlayer.ts`, styles in `src/styles/computer.css`). The child is always Team Past and the Computer player is Team Future. It copies the child's grade and subject. The choice is saved in `timeclash.practice`.
- **Hand-off:** `buildBattleData` gives `BattleSceneData.practice = { team, level, effects? }` only when the flag is on, the saved choice is `computer` and one saved player is named "Computer player". Names are 12 letters at most, so no child can match it.
- **Battle (`src/scenes/battle/flow.ts`):** on the computer's turn there is no pass screen, the dial and meter move by themselves (`computerAims`) while `overlay.showThinking` shows "Computer player is aiming", Fire stays off, and the shot flies through the same `launch` path as a child's. The reload (`computerReload`) shows "Computer player is thinking" and never a question card, choice or answer. It uses its own random stream (`RNG_SALT.computer`) and leaves the child's question history and level nudges alone. A wrong answer still reloads (Gate 2). Thinking time stays under `turnBudgetMs` (8 s) per computer turn.
- **Label:** the HUD cards, turn strip (`computerTurnBanner`), setup card and Victory all show `PRACTICE_BOT.displayName`.

## Disturbances: birds, gusts and recoil
Shots were too predictable, so three seeded nudges change where a shot lands (on by default; `DISTURBANCE` in `src/game/config.ts`, switched per match by `MatchOptions.disturbances`). The rules are pure functions in `src/game/disturbance.ts`; the scene only draws.
- **Level:** `levelForTurn(seed, turn)` draws low, medium or high (a third each) from its own salted stream. It scales the turn's gust push, bird turn and count, and recoil limits (`DISTURBANCE.levels`). `birdsForTurn`, `gustForTurn` and `recoilFor` take the level as an optional last argument and default to the turn's level. The gust carries its level (`Gust.level`, `GustHit.level`) so the scene draws a bigger cue for a stronger gust; each bird carries its `nudgeDeg`. The numbers below are the base numbers that a level multiplies (low is 1x, except the gust at 1.1x).
- **Birds:** `birdsForTurn(seed, turn)` gives one to three birds on seeded paths across the sky band (y 170 to 420), at 40 to 70 px/s, wrapping past each edge. `birdAt(bird, ms)` says where a bird is on the bird clock (ms since the turn's birds took off). The Battle scene keeps that clock (`disturbanceLayer.ts`; it stops while the game is paused) and hands it to `match.fire({ birdMs })`, so the flight meets each bird where it is drawn. A shell whose center comes within 26 px of a bird is turned 16 degrees (up if it skims over, down if it clips under) and keeps 85% of its speed. A bird bumps a shell at most once, and never in the first 250 ms (so it cannot stop a shot at the muzzle). The bird is never hurt: it spins, loses a few feathers and flies on.
- **Gust:** `gustForTurn(seed, turn)` gives one gust per turn: 150 to 250 px/s² sideways, either way, for 400 ms, starting 20% to 50% of the way through the shell's plain flight (so a flat shot meets it as surely as a lob).
- **Recoil:** after a fighter fires, its team's aim moves by `recoilFor(seed, turn, shotInTurn, role)`: a whole number between minus and plus the role's limit (`DISTURBANCE.recoil`; heavy weapons 3 degrees and 5 power, the archer and laser gun 1 and 1; mirror pairs share a row). Always clamped to `AIM`. The HUD sliders slide there over 320 ms (a jump with reduced motion), so the child sees it and can re-aim. The first kick of a match also puts "Kick! Your aim moved." in the message lane through `overlay.setCaption` (`BattleFlow.kickShown`, not stored; tests: `tests/scenes/battle/flowKick.test.ts`, `e2e/disturbances.spec.ts`). Mounted weapons have no recoil.
- **Honest preview:** `previewShot()` and the aim guide fly plain wind only. `simulateShot({ ..., disturbance })` takes the birds and gust as an optional input and adds `bumps` and `gust` to the result; the full arc trace after a shot shows what really happened.
- **Cues:** a bump shows a feather puff, the "Squawk!" word and a squawk sound; a gust shows streaks and an arrow sliding its way (3 streaks at low, 4 at medium, 5 at high, drawn bigger as the level grows), the "Gust!" word and a whoosh sound. Both sounds are made in code (`src/audio/sfx.ts`) and respect mute. The words show even with sound off.
- **Tests and the Computer player:** the Computer player aims with the plain physics and then gets nudged like a child. Rules tests that check exact flights pass `disturbances: false`. A browser test run starts with them off (the e2e hook's `setDisturbances` turns them on). The hook's `previewVictory(options)` opens the real Victory screen with made-up results, so a browser test can check its words and fit without playing a whole match.

## Key data shapes
```ts
type Team = 'PAST' | 'FUTURE';
type Player = { name: string; team: Team; grade: number /* 0 = K */; subject: 'reading' | 'math' | 'both' };
type AimInput = { angleDeg: number; power: number }; // angle 0 to 90, power 0 to 100
type Shot = AimInput & { team: Team; wind: number; turnNumber: number }; // one fired shot, replayable
type Match = { players: [Player, Player]; baseHp: Record<Team, number>; scrap: Record<Team, number>; turn: number; wind: number };
```
The full contract (every type, function signature, and rule) is in [src/game/types.ts](./src/game/types.ts). See [docs/CONTRACTS.md](./docs/CONTRACTS.md) for the reasons behind each choice.

Question and intro shapes are in [docs/BUILD.md](./docs/BUILD.md) and [docs/NARRATION.md](./docs/NARRATION.md).

## Determinism
Wind, birds, the gust, recoil, question order, and speech bubble choice use a seeded RNG (`src/game/rng.ts`). Physics uses a fixed 1/60 s step. The same seed and inputs give the same match.

## Storage keys (localStorage)
`timeclash.players`, `timeclash.introSeen`, `timeclash.settings` (mute, volume, captions, music, reduced motion, and `hideBonusRing`: a boolean, off by default, read with a validated check so any other value means off), `timeclash.history` (questions used, plus a short list of missed questions to ask again), `timeclash.camp` (one wallet per player name: Scrap in hand, lifetime Scrap earned, and the weapons and upgrades they own for each side, including weapons they made in the Weapon Workshop, plus the seed of the last match whose Scrap was added). Names match without caring about capitals or extra spaces. A plan for signed-in players and a SQLite database is in [docs/ACCOUNTS_PLAN.md](./docs/ACCOUNTS_PLAN.md)), `timeclash.bases` (up to three saved bases per player name and side, each a short list of bricks, plus which slot is chosen; at most 50 names; cleaned on every read), `timeclash.plan` (the last Battle Plan: biome, base spot, and Team Past's castle place; bad data falls back to Aspen Forest, Food Trucks and Village Wall, so an old plan with no castle place loads at Village Wall), `timeclash.levels` (a quiet level nudge per player name and subject: an offset from -2 to +2 and the last few answers, at most 50 names; after each 5 answers, 4 or more right moves up one step, 2 or fewer moves down one; never shown to a child), `timeclash.practice` (Play with: `{ opponent: 'person' | 'computer', level: 'easy' | 'medium' | 'hard' }`; only read while the Computer player choice is on), `timeclash.setupPicks` (the grade and subject each side picked at Setup, no names: `{ PAST?: { grade, subject }, FUTURE?: ... }`. Setup opens with these, so a family does not re-pick grades. Saved on "Let's clash!". Saved players still win. A side with a bad grade or subject is dropped and starts at the default. A `topic` field saved by the retired Focus switch, in these picks or in `timeclash.players`, is dropped on read, and old `math-3-division` style keys in `timeclash.history` are dropped too. "Clear my data" removes it), `timeclash.matchLength` (`'short' | 'normal' | 'long'`; saved on "Let's clash!"; anything else reads as Normal; "Clear my data" removes it). No personal data beyond first names the family types in. Nothing is sent anywhere.
